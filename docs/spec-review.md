# Quartermaster spec readiness review

Oct 7, 2026. For Liam (product owner) and the engineers building Phase 1.

This review covers `docs/spec.md`. It merges nine review passes (data model, security and tenancy, inventory math, UX and accessibility, integration fact-check, Phase 1 readiness, planning and freezer, offline and sync, product coherence). Where the spec is silent and the code in `src/domain` or `supabase/migrations` has already chosen a rule, this report adopts that rule and asks that the spec be amended to match. Where findings overlapped, they are merged. Every resolution below describes one data model.

---

## 1. Verdict

The spec is ready to start Phase 1 and not ready to finish it. The architecture (Supabase with row-level security per household, a React PWA, a pure domain layer) is right, and the migrations and domain code already follow it closely. Four things stop Phase 1 from reaching its own exit gate as written. The Phase 1 scope line leaves out the cook-week builder, container math and freezer shelf that "run a full cook week" needs. The Neelix export that supplies the 262 recipes, the staples, the freezer inventory and the price book is neither described nor in the repo. The offline design is one sentence, and the current data layer does not implement it (there is no write queue, and deletes are hard deletes). And the link from a recipe ingredient to an inventory item, plus the unit model every comparison depends on, exists in code but not in the spec, so two engineers reading the spec would build it two ways. None of these need a new design. Each has a concrete default in this report. The owner needs to act on four inputs (the Neelix export, a Supabase project and plan, an Instacart developer key, one hand-built cook-week PDF) and confirm the College Station facts that the demo seed invented. The build proceeds in local mode on the defaults until then.

## 3. Blockers and majors

### 3.1 Phase 1 scope, gate and owner inputs

#### Blocker: the Phase 1 scope line cannot meet its own exit gate

- Spec says: Phase 1 is "pantry, recipe bank, make-it-now and almost-there, single shopping list, Instacart send, price book, A/A+/A++, cook mode". Gate: "Liam and Sarah run a full cook week in the new app and Neelix is retired."
- Problem: a cook week needs the cook-week builder, batches with container math, the freezer shelf (which cook mode's end step writes and the Neelix import populates), plan-to-list subtraction and labels. None is in the scope line. Scenario 4 ("next week's dinners are already on the calendar") has no feature behind it. "Neelix is retired" is an owner action, not a test. The success criteria require voice (Phase 3) 90 days after Phase 2.
- Resolution: Phase 1 scope = Home (energy, tonight's pick, low/out count, shopping summary), Pantry with freezer shelf, Cook with suggestion feed, recipe bank, week plan view (manual placement), cook-week builder, cook mode, Shop with send and ordered section and price book, House, Import. Phase 2 = week auto-fill, Cheap week, Bad day, low-energy Home, freezer kit setup, ideas library, PDF layout match. Cook mode is tap-only in Phase 1 (steps, wake lock, timers, end-of-cook write). Scenario 4 becomes an opt-in tap "Plan next week's freezer nights" on the cook-week done screen, never automatic. Exit gate = (1) Neelix export imported with zero unresolved flagged ingredient rows; (2) one cook week with at least 3 batches planned and the freezer shelf showing the blocks after cook mode; (3) one list of at least 10 lines sent (sandbox link, MCP flow or text list) and marked ordered, then received; (4) depletion review completed for each cooked recipe; (5) no horizontal scroll at A++ on all five tabs at 360 px; (6) a change on Liam's phone appears on Sarah's within 5 seconds, and the RLS suite is green with two households seeded. Retiring Neelix is recorded after the checks pass. Success criteria: drop "using voice" from the accessibility line; keep the 90-days-after-Phase-2 date for the rest. Move "hands-free wake" from Phase 3 to Phase 4.

#### Blocker: the Neelix export is undocumented and absent

- Spec says: migration "reads an exported JSON file from Neelix and maps it table by table."
- Problem: the JSON shape is never described and no sample is in the repo. That one file is the only source for the 262 recipes, the 30 staples, the Souper Cubes inventory, the price book with dates, the Kroger search-term quirks and the open list. The importer cannot be finished against an unknown shape, and every Phase 1 check runs on empty data without it.
- Resolution: a versioned import contract `qm-import-v1` (zod schema) covering recipes, ingredients, items, freezer blocks, containers, prices, aliases, retailer search terms and list lines. The import screen is written against that contract. A Neelix-to-QM adapter is written against a hand-made fixture (5 recipes, 10 staples, 3 blocks) that includes the awkward ingredient lines ("1 (15 oz) can", "2 cans (15 oz) black beans, drained", ranges, "to taste"). The owner supplies the real export (section 2). Ingredient parsing is deterministic in-app first (`parseIngredientLine`); flagged rows are fixed by hand. Only if the flagged count is in the hundreds does a local script send the flagged lines to Claude in batches of 50 with a strict schema, using keys from `.env.local`. No Claude edge function in Phase 1. The Souper Cubes directory is skipped in Phase 1; later it is a static JSON with the allergy flag computed from the viewing household's rules, not hard-coded to coconut.

#### Major: no Supabase project, hosting target, auth redirect origin or keep-alive exists

- Spec says: "stays on Supabase's free tier", "$0", "GitHub Actions cron hits a lightweight endpoint", and nothing about where the static PWA is served.
- Problem: the connected org is on Pro with five active projects, so a new project there bills its own compute and the "$25 Pro bill" trigger is already met. Supabase does not host static sites, so Web Push, the service worker scope and the auth redirect list have no origin. No `.github` directory, `vercel.json` or `supabase/config.toml` exists. A keep-alive that only pings an edge function does not generate database activity and does not prevent the pause.
- Resolution: owner picks the project home (section 2). Either way: run `supabase init` and `supabase link`, apply the four migrations, regenerate `database.types.ts` against the real project. Hosting: Vercel Hobby (Netlify is equivalent), static `dist/`, a catch-all rewrite to `/index.html`, no-cache headers on `sw.js` and `manifest.webmanifest`, `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` as the only client env vars. Use the assigned `*.vercel.app` URL as the Supabase Site URL until a domain is bought. If the Free org is chosen, add `.github/workflows/keepalive.yml` the day the project is created: daily plus `workflow_dispatch`, a `curl -f` PostgREST read with the anon key (an RLS-filtered read still counts as activity), fail loudly. Add a weekly `pg_dump` job to an encrypted artifact or private repo because the free plan has no backups. Note the GitHub rule that scheduled workflows stop after 60 days of repo inactivity; Riker becomes the permanent runner. Rewrite the Hosting table to say "free tier if a free slot exists, otherwise about $10/month in the Pro org" and strike the "confirm invocation limit" to-do (500,000 per month, verified).

#### Major: the Instacart production key needs Instacart's review; the MCP fallback cannot be called from the app

- Spec says: Instacart Developer Platform products-link, "verify endpoint name"; the MCP connector as an alternate path.
- Problem: the endpoint is verified (section 5) but the production key sits in "pending approval" until Instacart reviews the app; the development key is self-serve, takes about a week, and only produces sandbox links. The MCP connector is a tool inside Claude chat sessions; a PWA cannot invoke it. The current adapter note promises the link "with the Phase 3 server piece".
- Resolution: the existing `RetailerAdapter` (`plan()` returning a `SendPlan` with method link/copy/share/print) gains an async path that calls a Supabase edge function `instacart-link` when `INSTACART_API_KEY` is set in function secrets, and falls back to the current search-plus-copy plan otherwise. `retailers.config.environment = development | production`. Line items use `item_retailer_links.search_term` as the name override and `items.barcode` as `upcs`. The MCP path is documented as "paste the copied list into a Claude chat", not an in-app feature. Add an Instacart row to the Risks table.

#### Major: sign-in, invite acceptance and first run are not defined, and member invites are scheduled after the gate that needs them

- Spec says: "the invitee signs in, lands in an empty household"; owners "invite/remove members"; invites are Phase 2; first-run is "five screens, all voice-answerable"; nothing names the auth provider.
- Problem: Sarah must be an editor in Denton for the Phase 1 gate. The only invite described creates a new household, which is wrong for her. Magic links open in Safari, not the installed PWA, so the home-screen app stays signed out. Passwords fight the accessibility goals. Google-only sign-in forces Sign in with Apple at the Capacitor wrap. Supabase sign-ups are open by default, which is what makes any Phase 3 Claude cost reachable by strangers. `accept_invite` compares `auth.jwt()->>'email'`, so the provider must yield a verified email. The client currently runs on a hard-coded demo session.
- Resolution: sign-in is a 6-digit email one-time code (`signInWithOtp` then `verifyOtp` type `email`), no links, no passwords; long refresh-token sessions so codes are rarely re-entered. "Allow new users to sign up" is off. Phase 1 users (Liam, Sarah) are created by the owner in the Supabase dashboard or by a local script with the service role; Phase 2 adds an `invite-send` function that calls `auth.admin.inviteUserByEmail` after an as-user check that the caller is an owner. Custom SMTP (Resend free tier) before Sarah onboards; Inbucket for local testing. Google optional later; Apple added with the Phase 4 wrap. Routes added to Phase 1: `/auth` (one screen, 64 px primary action), `/setup` (shown only when the user has zero memberships; five screens: name, timezone and ZIP; members as invite links; retailers; allergies; starter staples and optional recipe bank import; tap and type only until Phase 3), `/join/:token` (shows household name and role, Accept or Decline; if signed out, the token is held through sign-in and the user lands in that household). Membership invites move to Phase 1. A `SessionProvider` reads the Supabase session in Supabase mode; local mode keeps `DEMO_USER_ID` for demos and tests. On household switch, navigate to Home.

#### Major: several specified features belong to no phase

- Spec says: nutrition on every card, Stretch and Swap, Cheap week, Bad day, energy selector and effort score, low-energy Home, freezer kit setup, ideas library, labels and PDF, read-aloud, hand toggle, dyslexia font. The roadmap names none of them.
- Problem: an engineer either pulls nutrition (an external key plus a mapping for 2,600 ingredient rows) into Phase 1 or ships a card that contradicts the section.
- Resolution: Phase 1 keeps what the scaffold has (energy selector, effort score, A/A+/A++, dark and high-contrast themes, reduced motion, hand toggle, reading font) plus label text and a `/print` route; recipe cards show cost per serving when the price book knows it and the built-in nutrition estimate only when it resolves (section 2). Phase 2: freezer kit setup, ideas library, low-energy Home, Bad day, Cheap week, week auto-fill, nutrition via FDC with the confidence mark and diet rule flags, PDF layout match. Phase 3: Stretch and Swap (needs Claude for candidates), read-aloud, receipts, barcode, voice. Phase 4: hands-free wake, native haptics. Until FDC lands, the Phase 2 rules editor's diet row is inert and the UI says so. Record this table in the roadmap section.

### 3.2 Data model: tenancy, columns and reference data

#### Major: the one-policy RLS claim recurses, cannot create a first household, and is too coarse for the roles table

- Spec says: "a user can read a row if a membership row joins them to its household ... applied to every table"; insert/update for owner or editor; delete households or memberships only as owner.
- Problem: applied to `memberships` the policy selects from `memberships` inside its own policy, which Postgres rejects (42P17), and every other table joins `memberships` too. A new user has no membership, so nobody can insert the first household or the first membership. The roles table promises owner-only writes on retailer connections and member management that the sentence does not express, says nothing about editors deleting rows, and lets an editor insert an activity row carrying Sarah's user id or update their own role. Riker is "editor" yet "cannot send or delete".
- Resolution (already in `0002_rls.sql` and `0003_functions.sql`, to be written into the spec): `SECURITY DEFINER` helpers `app.user_household_ids()` and `app.has_role(household_id, roles[])`, owned by postgres, `stable`, `set search_path = ''`, with `auth.uid()` referenced only inside them. Tenant policies use `household_id in (select app.user_household_ids())`; the `memberships` policy is `user_id = (select auth.uid()) or household_id in (select app.user_household_ids())`. Index `memberships (user_id, household_id)`. Households and the first membership are created only by `app.create_household(name, timezone, zip)`; memberships otherwise come only from `app.accept_invite(token)`. Denton is seeded through the same path. Role matrix: roles `owner | editor | viewer | agent` (agent already in the enum; its triggers wait for Riker). Tenant data tables: SELECT any member; INSERT and UPDATE owner or editor; no client DELETE on any tenant table (delete is `deleted_at`, an update). Owner-only: `households` UPDATE, all writes on `retailers`, `memberships` role changes and removal of others, `invites`. A member may remove their own membership unless they are the last owner (trigger, Phase 2). Actor columns: `activity_events` and `partner_turns` carry `with check (user_id = (select auth.uid()))`, and the sync RPC forces `actor_user_id := auth.uid()` and restricts `source in ('system','agent')` to the service role or the agent role. User-scoped tables (`user_prefs`, `push_subscriptions`, `notification_prefs`) use `user_id = auth.uid()`. Viewer is SELECT only everywhere; the UI hides buttons but RLS is the enforcement.

#### Major: child tables lack `household_id`, and global reference data has no home

- Spec says: "Every tenant table carries household_id", yet `item_aliases`, `item_events` and `recipe_ingredients` have none, and the canonical recipe bank, the barcode cache and USDA data belong to no household.
- Problem: policies that join through the parent are slower and a second pattern; a denormalized column with no constraint lets a client attach an alias to another household's item; Realtime filters and the IndexedDB pull both need the column. The recipe bank copy for College Station has no source that RLS allows anyone to read.
- Resolution: `household_id NOT NULL` on every child table (`item_aliases`, `recipe_ingredients`, `activity_events`, `containers`, `receipt_lines`, `list_lines`) with composite foreign keys `(parent_id, household_id) REFERENCES parent (id, household_id)`; parents get `UNIQUE (id, household_id)`. Rewrite the rule as: every tenant row carries `household_id`; child tables denormalize it so RLS and realtime never join; a short list of global reference tables has no `household_id`, is SELECT for `authenticated`, and is written only by the service role: `recipe_library`, `recipe_library_ingredients`, `product_cache` (keyed by barcode; a UPC's product name is not tenant data, so the spec's "per household" at line 409 changes to "global, read-only to clients"), `usda_foods`. Client rule: one `db(householdId)` accessor appends the household filter to every query and the Dexie mirror is partitioned per household.

#### Major: no audit or sync columns, and no tombstones

- Spec says: only `item_events` and `partner_turns` list `created_at`; offline is "last-write-wins on the row with the event log keeping both sides".
- Problem: last-write-wins needs a comparable `updated_at` on every synced table, client-generated ids for queued inserts, and tombstones so a delete reaches an offline mirror. Retrofitting after Phase 1 data exists is painful.
- Resolution: standard column set on every tenant table: `id uuid` (client may supply), `household_id`, `created_at`, `created_by`, `updated_at`, `updated_by`, `deleted_at`. One generic `set_updated_at` trigger. Clients pull `WHERE updated_at > last_pull` including tombstones; RLS and UI treat `deleted_at IS NOT NULL` as gone; a Phase 3 purge hard-deletes tombstones older than 30 days. No optimistic locking: the server sets `updated_at` on apply, queued writes carry `client_written_at` for ordering, and mismatches are logged (section 3.7).

#### Major: invites are two flows with no table or token model

- Spec says: "invite a new household by email or a one-time link" and "owner: invite/remove members".
- Problem: creating a tenant plus its first owner and adding a user to an existing household share one word. Neither has a persisted token, expiry, role or acceptance record, and an invitee cannot read an invite row under membership RLS.
- Resolution: `invites (id, kind member | household, household_id, email NULL, role, token_hash, invited_by, expires_at default now() + 7 days, accepted_at, accepted_by, new_household_name NULL, created_at)`. The raw token (32 random bytes, base64url) is shown once; only its sha256 is stored. `app.accept_invite(token)` is `SECURITY DEFINER`: valid, unexpired, unused; if `email` is set, it must match the caller's confirmed email; `member` inserts the membership; `household` creates the household owned by the invitee and runs the starter kit (seed staples, default locations, kit containers, library recipes with plating notes stripped). Owners of `household_id` may SELECT, INSERT and DELETE their invites; nobody else reads the table. College Station setup uses the `household` kind.

#### Major: the shared recipe bank and "send recipe to household" have no mechanism

- Spec says: recipes are copied, never shared; College Station gets "the same bank minus Denton-specific plating notes"; a later "send recipe" copies again.
- Problem: under the one-policy model Liam cannot insert into College Station's `recipes` and College Station cannot read Denton's. The copy source (pristine import or Denton's edited rows) is unstated, as is what gets stripped.
- Resolution: the global `recipe_library` and `recipe_library_ingredients` (already in the migration) are the single explicit exception to the one-household rule. Phase 1: the in-app import writes Denton's `recipes` and `recipe_ingredients` under RLS; the library stays empty. Phase 2: a local script run by the owner with the service role loads the cleaned, structured Denton recipes into the library with `plate_notes`, person ids, `cost_per_serving_cents`, `item_id` and image paths stripped; `copy_library_recipe` copies selected rows into a new household, which turns the open question "full bank or trimmed set" into a checkbox at first run. `recipes.library_id` records provenance. Household-to-household send (`recipe_transfers`) is deferred past Phase 2 with the same strip list.

#### Major: budget, plating and person tags each have two homes

- Spec says: budget on `households` and as a `budget` rule; plating as a rule type and in `persons.plate_profile`; `memberships.person_label` alongside `persons`; items have no person column.
- Problem: two writers update different places and the budget bar reads the wrong one; copying recipes carries dangling person keys.
- Resolution (matches the migration): `households.budget_monthly_cents` and `budget_warn_pct` (default 80); `rules.type = allergy | prep | diet | cuisine` with a documented payload per type; plating only in `persons.plate_profile = {portion_multiplier numeric, richness lighter|standard|richer, notes}`; `memberships.person_id` FK replaces `person_label`; `persons.user_id NULL` links a person to a member; `items.person_id NULL` (NULL means ours); the UI renders "mine", "<name>'s" or "ours" relative to the viewer's linked person. `recipes.plate_notes` is keyed by `person_id` and stripped on any copy to another household.

#### Major: item category is load-bearing and never enumerated

- Spec says: routing by category, budget by five groups, shelf life "by category", aisle grouping, 30 seeded staples, "always have", none defined.
- Resolution (matches the code): `items.category` is a fixed enum: produce, dairy, meat, seafood, frozen, bakery, pantry, spice, condiment, beverage, snack, paper, cleaning, household, pet, pharmacy, other. Spend group map: the first eleven are groceries; paper and household are household; cleaning, pet and pharmacy map one to one. Routing "food" is the groceries group. Shelf-life defaults per category (`SHELF_LIFE_DAYS_BY_CATEGORY`: produce 7, dairy 14, meat 3, bakery 5, pantry 730, others none). Aisle order is `retailers.config.aisleOrder`, editable. `always_have` items count as in stock for matching regardless of status and still go on the list when Out. A small built-in non-item list (water, ice) never blocks a match. A 30-item starter staples list (status mode) ships for new households; Denton's real staples come from the import.

#### Major: nothing verifies RLS

- Spec says: the policy pattern "is the whole multi-household security model"; Phase 1 has one household.
- Problem: a table created without `ENABLE ROW LEVEL SECURITY` is fully readable through the anon key, and a missing policy is invisible until College Station joins.
- Resolution: migration template: every `create table` is followed in the same file by `enable row level security` and its policies; `revoke all on all tables in schema public from anon` with matching default privileges; `revoke execute on all functions in schema public from anon, public`; `search_path = ''` on every definer function. CI: a Vitest suite signs in as two seeded users in two households and asserts zero cross-household rows on every table, that an insert with a foreign `household_id` fails, that viewer writes fail, and that `memberships` reads do not recurse. Run the Supabase security advisors on every migration. "RLS suite green with two households seeded" is part of the Phase 1 gate.

#### Major: edge-function principals are unstated

- Spec says: "every row they touch still passes through row-level security as the signed-in user", yet the notification batch, the price check, the keep-alive and invite emails have no signed-in user.
- Resolution: a function inventory with a principal per function. Phase 1: `instacart-link` (as user: anon key plus forwarded Authorization; first lines call `auth.getUser()` and return 401 without one). Phase 2: `invite-send` (service role, after an as-user owner check), `price-check-weekly` (service role, cron, only if the owner turns the web check on; iterates every household with its own ZIP). Keep-alive is GitHub Actions with no function. Phase 3 functions join the list then. The rule that matters: a service-role function never takes `household_id` or `user_id` from the request as authority. Realtime uses `postgres_changes` on tenant tables; no Broadcast in v1.

### 3.3 Ingredient matching, units and the suggestion engine

#### Blocker: nothing links a recipe ingredient to an inventory item, and there is no unit model

- Spec says: `recipe_ingredients (recipe_id, ingredient_name, amount, unit, item_match_hint, optional)`; make-it-now needs "status OK or count at or above the recipe amount"; plan-to-list shows "need 3 lb, have 1 lb, buy 2 lb"; depletion shows "the item it maps to". Items carry one free-text unit (cans, lb, oz).
- Problem: no column stores the resolved item, `item_match_hint` has no defined type, `item_aliases.source` has no value for a recipe-side fix, and no rule says what happens when a recipe says cups and the pantry says cans. One engineer builds a runtime fuzzy matcher that cannot be corrected; another persists an FK that is never backfilled. After the import, 2,600 ingredient rows meet a 30-item staples grid and "make it now" returns nothing.
- Resolution (matches `matching.ts`, `units.ts` and `CONTRACTS.md`): `recipe_ingredients.item_id uuid NULL` (same household), `canonical_name` (one deterministic normalizer: lowercase, strip quantities and descriptors, drop parentheticals, singularize; shared by aliases, allergy matching and FDC overrides), `match_confidence`, `original_text`. Resolution order at query time: persisted `item_id` > alias > exact canonical name > fuzzy at or above 0.8 > always-have > unresolved; the persisted `item_id` is the override, so new items link without a backfill job. A fix on the recipe card writes `item_id` and an `item_aliases` row (sources now include `ingredient` and `manual`). `item_id` is nulled on copy to another household. After the import, an "unlinked ingredients" review sorted by recipe count lets the owner create common items in one pass. ### 3.7 Offline, sync and realtime

#### Blocker: there is no write queue

- Spec says: "an IndexedDB mirror and a write queue ... writes apply locally first, sync when online."
- Problem: the build has two swappable adapters. In Supabase mode every read hits the network and every write throws on failure; `db.ts` has no outbox; nothing moves rows between adapters. Opening Shop inside Kroger with no signal shows nothing. Every feature write already goes through `Collection` via `replaceRow`, `insertRow`, `deleteRow` and `logEvent` in `src/data/mutations.ts`, so the retrofit touches the Supabase adapter and that helper file, not every screen.
- Resolution: Phase 1 ships one Supabase-backed repository that is cache-through. Reads come from Dexie, hydrated by a full per-household pull of every tenant table on app open, on `visibilitychange` to visible, on the `online` event and after each successful flush (under 5,000 rows per household, so no incremental cursor yet). Writes apply to Dexie first, then append to a Dexie `outbox` store `{opId uuid, householdId, table, rowId, kind insert|patch|delta|softDelete, payload, baseUpdatedAt, clientAt, attempts}`. A flusher drains FIFO per household when online, refreshing the session once on a 401. A header chip shows "N changes waiting". `LocalRepository` stays as the no-backend demo. The Dexie database name is keyed by user id and deleted on sign-out. Spec sentence: the mirror and queue ship in Phase 1; Phase 4 "hardening" means conflict UI and incremental pulls.

#### Major: last-write-wins has no clock and full-row upserts clobber the other phone

- Problem: `app.set_updated_at` overwrites every timestamp, so "last write" means "last to arrive"; `Collection.put` upserts whole rows, so Sarah's stale full row erases Liam's newer `use_by`.
- Resolution: queue entries for existing rows are patches (changed columns only); `put` is used only for new rows with client-generated ids. Each op carries `baseUpdatedAt`. Flush goes through one RPC `apply_ops(jsonb)`: if `baseUpdatedAt` equals the row's `updated_at`, apply; otherwise apply in arrival order (what the spec says) and insert an `activity_events` row with `source = 'sync'` holding both values ("Sarah set Out Sat 9:12, Liam set OK Sun 2:05; kept OK"). Spec sentence: "last write wins per field; the server clock decides; mismatches are logged as sync events." A `client_updated_at` column and column-wise merge are Phase 4.

#### Major: counters are written as absolute values with no op id

- Problem: two phones press Eat 1 on a 3-count block offline; both enqueue `count_remaining = 2`; truth is 1. A retried flush applies a delta twice. Undo by restoring `before` erases the other person's change.
- Resolution: `activity_events.op_id uuid` with a unique index now; `delta numeric` restored. `apply_ops` inserts the activity row first with `on conflict (op_id) do nothing` and skips the op if it existed. `items.qty` and `freezer_blocks.count_remaining` are delta ops applied server-side as `greatest(0, qty + delta)` with status recomputed in the same statement (the same `deriveStatus` rule as the domain layer); everything else is a patch. Undo of a delta is a compensating delta, never a restore of `before`; undo of a field patch restores `before` only when the row's `updated_at` still equals the event's `after` timestamp, otherwise it surfaces as a conflict. This is also the fix for the activity feed's `undoEvent`.

#### Major: hard deletes are invisible to other devices

- Problem: `Collection.remove()` issues a real DELETE; RLS grants DELETE to editors on every tenant table; a DELETE payload carries only the primary key, so the household filter never matches and the other phone keeps a ghost row.
- Resolution: clients never hard-delete tenant rows. Undo of an insert is a `softDelete`. `delete_roles = nobody` for all tenant tables in `apply_tenant_policies`; `remove()` stays only for `push_subscriptions` and `user_prefs`. The existing partial index on `list_lines` already ignores tombstones, so re-adding an undone line does not collide. Tombstone purge is Phase 3.

#### Major: the PocketBase exit plan is not feasible

- Resolution: exit path is any Postgres host (section 2). Build rule becomes: nothing outside stock Postgres, PostgREST, GoTrue and supabase-js; `jsonb` not arrays; `text + CHECK` not `CREATE TYPE`; `user_id` columns are uuid with no FK to `auth.users`, plus a `profiles (user_id PK, display_name, created_at)` row created at signup; storage columns hold object paths (`image_path`, not `image_url`) and the client builds URLs; scheduled jobs run from the external cron; edge functions stay thin; retailer and Claude calls stay behind adapters. Drop PocketBase from the spec and the `0004_realtime.sql` comment.

1. Phase 1 serves Denton only; the College Station rows in the demo seed are placeholders and the real household is set up in Phase 2.
2. Both households use phones first; which platform is unknown, so every voice or sensor feature has a tap path that is the primary design until the owner says which phones are in use.
3. Each household stays under about 5,000 rows across all tenant tables, so a full per-household pull on open is acceptable and incremental sync can wait for Phase 4.
4. The Neelix export has the shape reconstructable from Neelix's source, and the versioned adapter absorbs any difference when the real file arrives.
5. The Supabase free-plan rules verified in October 2026 (7-day pause, 90-day restore, 500,000 invocations, no backups) hold through Phase 2.
6. The Instacart development key arrives within about a week and a sandbox link is enough for the Phase 1 gate; production approval has no deadline.
