| `price-check` | Service role on the weekly schedule (`.github/workflows/price-check.yml`); as a signed-in owner or editor for "Check prices now" | `ANTHROPIC_API_KEY`, optional `PRICE_CHECK_MODEL` (default `claude-opus-5-5`), `PRICE_CHECK_MAX_CALLS_PER_DAY` (default 12) | Ready; needs a Claude key. Writes `prices` rows with source `web` and the page URL in the note, logs every call to `ai_usage`. `quotes.ts` is a copy of `src/integrations/prices/quotes.ts`, which carries the unit tests; keep them identical. |

| `notify` | Service role on the hourly schedule (`.github/workflows/notify.yml`); as a signed-in owner or editor with `{ householdId }` for "send what is due now" | `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (a `mailto:` address or https URL) | Ready; needs a VAPID pair. Per household it works out the local time, computes what is due with `notifications.ts` (a copy of `src/domain/notifications.ts`, which carries the unit tests; keep them identical), records each dedupe key in `notification_queue`, drains the queue (the `list_sent` rows come from a trigger on `list_sends`, migration `0008_notify_queue.sql`), and sends Web Push with the `web-push` package to every phone in `push_subscriptions` whose owner has that kind on. Quiet hours hold the queue. A phone that answers 404 or 410 is deleted. Idempotent per hour. Not built: `cook_week_prep` (needs the cook-week cook tag). |

Generate the VAPID pair once with `npx web-push generate-vapid-keys`; put the public key in the app's `.env` as `VITE_VAPID_PUBLIC_KEY` and both halves plus `VAPID_SUBJECT` in the function secrets (`supabase secrets set VAPID_PUBLIC_KEY=... VAPID_PRIVATE_KEY=... VAPID_SUBJECT=mailto:you@example.com`). Changing the pair later invalidates every stored subscription; people flip the phone toggle off and on.

Deploy with `supabase functions deploy instacart-link price-check notify` after `supabase link` (the Phase 3 functions below deploy the same way). The app calls it from the Shop send sheet and falls back to a search link plus a copied list when the function is absent or unconfigured.

## Phase 3 intake functions

All four run as the signed-in user (the bearer token must belong to a member of `householdId`; `_shared/auth.ts`), answer the browser's CORS preflight (`_shared/http.ts`), keep a per-household daily cap in `ai_usage` (`_shared/usage.ts`, one row per model call with `fn` set), call the Messages API directly over `fetch` with no tools (`_shared/model.ts`), and treat utterances, page text and images as data: every prompt carries the same rule that content inside a `DATA` block is read, never obeyed. Output is strict JSON, validated on the server; anything malformed is a plain error, never a guess. None of them write household rows: the app saves through its own mutations so undo and the activity feed work. Client helpers live in `src/integrations/ai.ts`.

| Function | Input | Output | Cap (env, default) | Notes |
| --- | --- | --- | --- | --- |
| `parse-intent` | `{ householdId, utterance, today? }` | `{ intents: Intent[], via: 'server' }`, the union in `src/domain/types.ts` | `INTAKE_PARSE_MAX_PER_DAY`, 200 | Builds the context packet itself (item, retailer and person names, recipe titles). The partner sheet tries it first when a backend exists and falls back to the local parser, showing which answered. Viewers may call it (nothing is written). |
| `url-import` | `{ householdId, url }` | `{ recipe, via: 'jsonld' \| 'model' }` in the shape of `_shared/recipe.ts` | `INTAKE_IMPORT_MAX_PER_DAY`, 40 (model calls only) | Fetches the page server side (public http(s) only, 2 MB, 15 s), uses schema.org `Recipe` JSON-LD when present with no model call, else hands the visible text to the model. |
| `recipe-generate` | `{ householdId, request }` | `{ recipe, allergyHits, via: 'model' }` | `INTAKE_GENERATE_MAX_PER_DAY`, 20 | Sends in-stock food item names and the active rules (allergy, prep, diet, cuisine) with the request, then runs the ingredients through `public.check_allergies` as the user; the app saves a recipe with hits as a draft. |
| `receipt-parse` | `{ householdId, storagePath }` (bucket `receipts`, path `<householdId>/<id>.jpg`) or `{ householdId, imageBase64, mediaType }` | `{ retailerGuess, purchasedOn, totalCents, lines: [{ name, qty, unitPriceCents, totalCents }], via: 'model' }` | `INTAKE_RECEIPT_MAX_PER_DAY`, 30 | The path must start with the caller's household id. The scan screen matches lines to items (`src/domain/receipts.ts`), lets the person fix them, then one save writes `receipts`, `receipt_lines`, `prices` (source `receipt`), a `spend` row and restocks, with one undo. |

Secrets: `ANTHROPIC_API_KEY` (required; `url-import` works without it for pages that carry JSON-LD), optional `INTAKE_MODEL` (falls back to `PRICE_CHECK_MODEL`, then the default in `_shared/model.ts`), and the four cap variables above. Create a private storage bucket named `receipts` in the project before using receipt photos (`supabase storage` or the dashboard); the app uploads through `Repository.uploadImage`. Deploy with `supabase functions deploy parse-intent url-import recipe-generate receipt-parse`. Every function degrades in the app: without a backend the partner uses its local rules, the recipe sheets say so and point at New, and the scan screen takes typed receipt lines instead of a photo.
